1) Deskripsi Perubahan

Adds a demo build of the Android app. `npm run build:demo` (or `scripts/android-build.sh demo`) produces an APK in which the whole field flow can be clicked through on a phone with no Cantol, no hotspot, no GPS and no backend. It implements all eleven screens of the mock, plus the manual-address and diagnostics screens behind the Cantol help card and a demo-only controls screen, with the behaviour of `mobile-ui-spec.md` and `mobile-tracking-mode.md`. A normal build is unchanged: it opens on the self-test only, with digest `f7f47846`, and the demo code is not in its bundle.

- **Switch.** `VITE_DEMO=1` is replaced by a constant at build time and `main.tsx` imports the demo entry through a dynamic `import()` behind it (ADR-007, Accepted).
- **Interfaces.** `CantolLink`, `Gnss`, `HotspotAssistant` and `SurveyApi` plus the local `AppStore` are defined in `mobile/src/core`; the screens depend only on them (through a `Services` context and a small `AppConfig`) and carry no demo code. The simulated implementations are in `mobile/src/demo`; TASK-005 to TASK-007 add the real ones behind the same shapes.
- **Real, not simulated.** The wizard as a pure reducer (the ADR-006 states, a 30 s silent recovery), route guards and Android Back, the local store (Dexie), the survey payload (tested against a hand copy of `pdSurveySchema`), severity (the WASM `classify`), and the tracking rules (new Rust in `cantol-dsp`, exported through `cantol-wasm`, with golden vectors for the exact boundaries).
- **Simulated.** The hotspot, Cantol (discovery, handshake, status, pulses with the fields of the real protocol messages), GPS (with a walker for tracking), the asset list and the upload. One seeded world model drives the simulated Cantol and GPS, so a walk gives the same trend words every time. Nothing makes a network request and there is no API key.
- **Packaging.** Launcher icon generated from the mark, dark launch screen and system bars (resources only), `@capacitor/app` and `@capacitor/status-bar` added. No Kotlin change, no manifest change, no new permission.
- **Verification tooling.** `npm run verify:demo` drives the demo in headless Chromium on a fake clock and checks every screen (see section 5).

4) Snapshot Kode (Before -> After)

4.1 The build switch

File: mobile/src/main.tsx

Before:
```
createRoot(container).render(<StrictMode><App /></StrictMode>);
```

After:
```
if (import.meta.env.VITE_DEMO === '1') {
  void import('./demo/boot').then(({ bootDemo }) => bootDemo(container));
} else {
  createRoot(container).render(<StrictMode><App /></StrictMode>);
}
```

Measured on the normal bundle against a clean build of `master`: the same set of files, `index.js` identical in size (232,093 bytes), no demo string, no font, no router. The WASM grew by 2,731 bytes (the trend rules), the self-test worker by 4.7 KB (the trend vectors), the CSS by 2.3 KB (Tailwind generates the utilities used anywhere in the source tree).

4.2 The tracking rules and their vectors

File: mobile/rust/cantol-dsp/src/trend.rs and mobile/rust/vectors/trend/cases.txt

Before: `cantol-dsp` held only severity classification.

After: window peak, live level, live trend, segment trend, mark value, peak index and guidance, with the design's thresholds as named assumption constants, and 56 vector cases covering the exact boundaries:
```
live_trend 10 10 10 11.5 11.5 11.5 = rising     # exactly +1.5 dB
segment 13 10 = falling                         # exactly -3 dB
guide 40 46 = trend_only                        # exactly 6 dB below: not "more than 6"
guide 43 46 = at_peak                           # exactly 3 dB below
```
The self-test digest is unchanged, `f7f47846` (old and new are the same): like the classify cases, the trend cases are checked and not hashed. A test pins it. The self-test shows one more row, `trend/cases`.

4.3 Auto-marking in GPS distance mode

File: mobile/src/core/tracking.ts

Before (first version): mark a station after three consecutive fixes inside the 5 m band.
After: mark it after seven consecutive fixes inside the band that lie within 3 m of each other (a dwell), or when the operator walks through and out of the far side of the band. Reason: the value of a mark is the window peak of the last five seconds, and with a mark taken during the walk-up the P3 mark (on a falling flank) was 5 to 6 dB too high. Now every mark is within 1.6 dB of the simulated level at its station, in both position sources.

4.4 The welcome animation

File: mobile/src/core/guards.ts

Before: a signed-in user at `/login` was redirected to the wizard. Signing in sets the operator before the Login screen has moved on to `/welcome`, so the redirect always won and the welcome animation never played.
After: `/login` stays open when signed in (it is also how an operator is switched). The browser verification asserts that the welcome screen is shown.

4.5 The build script

File: mobile/scripts/android-build.sh

After: `scripts/android-build.sh [demo] [install]`; `demo` runs `npm run build:demo` and leaves the result as `app-demo-debug.apk` next to `app-debug.apk`.

6) Assumptions

Recorded here instead of asking, as instructed. Every one is also flagged where it lives.

1. `pd_magnitude` for a recording is the window peak (open question 1 in the spec). The tracking sample is also the per-second window peak.
2. `surveyed_at` is the phone's clock when the recording finished; for a walk, when Finish was confirmed.
3. A GPS fix of 25 m or better makes the app ready; 10 m or better is needed for GPS distance, otherwise the walk uses point marks and says so.
4. Auto-marking: five stations in a 5 m band, seven still fixes within 3 m (a dwell), or walking through; the 20, 30 and 40 dBmV warning presets; a condition edit on a walk applies to the strongest mark only.
5. `/tag` and `/surveys` need only the operator, not the wizard at READY, so a recording already in the store is not lost when the link drops. Back goes to the parent screen of the flow, not through browser history, because the wizard replaces history entries.
6. The Peak tile is the highest level of the last 10 s; the plot shows the last 3 s; the plot scale steps through 30, 50, 70 and 100 dBmV; Rate and Noise are the latest `Status` values; the mains frequency label is a fixed 50 Hz.
7. Simulation constants: noise floor about 6 dBmV; peak width 0.18 of the span; a source is seen within 25 m of a route; pulse rate 40 plus 10 per dB above the noise, at most 600 per second; phase in two lobes inside 70 to 110 and 250 to 290 degrees; amplitude up to 3 dB below the level; a slow drift of under 0.7 dB; GPS accuracy about 4 m with sub-metre jitter, first fix after 1.5 s; the walker at about 1.2 m/s, holding 10 s at the start and at each measurement point (a walk takes about 100 s); the hotspot turns on 2.5 s after the settings are opened; Cantol is found after 4 s with RTT 4 ms; a manual address works only for 192.0.2.10; an upload takes 350 ms.
8. Placeholders: hotspot name `DEMO-hotspot`, password `demo-placeholder`, address `192.0.2.10` (an RFC 5737 documentation address), device id `DEMO-001`, skip-sign-in operator `demo@example.invalid`.
9. The launcher icon is the mark in amber (`#F5A623`) on `#0A0D10`, as the web's brand mark is amber; the design system does not name the colour.
10. The "larger font setting" is emulated by setting the root font size to 130 percent; all text sizes are in `rem`, so they follow it. Android's own text zoom was not used.
11. Fonts: Big Shoulders 700 and 900, IBM Plex Sans 400, 500 and 600, IBM Plex Mono 400 and 500, Latin woff2 only (the weights the screens use; Plex Sans 700 and Plex Mono 600 are not used).
12. react-router 8 with a hash router; Dexie 4; zod and playwright-core as dev dependencies only.
13. `Fast recording` is on by default and the note written into the survey states the real window length (10 s), not 60 s.

7) Deviations and decisions the user should know

- **Branch base.** The branch is off master (`ec85752`), as asked. It also contains the two docs commits of `docs/task-004-phone-selftest` (the phone self-test record), cherry-picked as `f2e0a7c` and `0211cbd`, because that branch was never pushed or merged and this work updates the same lines and the same CHANGELOG anchor. The local branch can be deleted.
- **Order.** The Rust trend rules were committed (`6982e43`) between M2 and M3 instead of in M4, because the Live and Tag screens use `window_peak`; the tracking screens still came in M4.
- **No haptics.** The spec's one-time warning alert says "visual banner, haptic, optional sound". Haptics were ruled out, so the alert is a banner plus the optional sound.
- **One extra demo control**, "Mains reference locked", because the spec defines what Live does when it is off.
- **The auto-mark rule** is a refinement of "marked when the chainage passes them" (section 4.3).
- **Two plugins and the icon and launch resources ship in the normal APK too**, because the Android project is shared. They add no permission. The normal APK is 4,203,680 bytes against 4,228,428 on master.
- **A hook** `window.__everlineDemo` (demo build only) lets the browser verification force failures without clicking through the controls screen.
- **The Phase 0 self-test screen** overflows by up to 12 px at 360 px wide with a 130 percent font. It is existing UI that must not change in the normal build, so it is excluded from the layout assertions and logged in TECHNICAL_DEBT.
- **Problems the verification found and fixed**: the welcome animation never played (guard race, 4.4); a link only 26 px high on the Ready screen; the waiting screen not saying that only a manual address was being tried; marks that were biased on a falling flank (4.3); an XML comment with two hyphens that broke the first real Gradle build; a cut-off search placeholder; and, in the verification itself, a reduced-motion check that passed without measuring anything, and a preview server that was left running.

8) Not verified

- The app on a phone: no device was attached. The Android pieces that cannot run in a browser (`SystemBars` and `StatusBar` calls, the hardware Back button through `@capacitor/app`, the launch screen, the launcher icon, resume from the background) were built but not seen working.
- The sound cue: the pitch function and the "no audio before a tap" path are tested; no sound was heard.
- "Copy password" (the clipboard) was not exercised.
- Other phones, Android's own font scale, older WebViews. The browser checks used Chromium 153 at two sizes.
- The light palette's contrast was not recomputed; it is the palette of the design system, still awaiting approval.
- Real hotspot, Cantol, GPS and backend behaviour: not the demo's job (`mobile/docs/operations/demo-build.md`, "What the demo cannot tell us").
