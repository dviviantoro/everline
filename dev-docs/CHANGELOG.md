### Added + fixed — device, mobile and pd-simulator: the Cantol program run on a real Red Pitaya (five SCPI assumptions corrected), a replay of pd-simulator, a web version of the field app, and saved board access (TASK-006 partly, 2026-11-21)
- Requested by the user: install the Analog Discovery 2 (AD2) driver and make `pd-simulator/` work; enter the Red Pitaya and save the login in the repository; "make simulation what everline mobile apps do with pd-simulator" (a web version of the app if the phone app cannot run here). ADR-012 (Proposed), ADR-011 decision 8 rewritten from measurements.
- **Not done: the AD2 driver.** This machine is `aarch64`; the installers in `~/Downloads` are `amd64` and cannot be installed here. Digilent's arm64 packages are behind a signed-in download (every scripted request gets 403; not worked around). The AD2 was also not seen at first: `lsusb` listed no Digilent device and the kernel log had no USB attach event. **After the user replugged it, it enumerated** (`0403:6014`, Digilent). **Later, with the user's arm64 packages:** Adept runtime 2.27.9 installed with `dpkg`; `libdwf.so` 3.25.1 and the WaveForms `firmware/` folder copied to `/usr/local` (the WaveForms `.deb` itself needs `libc6 >= 2.41`; this machine has 2.39); DWF named the device (AD2 rev C), opened it once, and pd-simulator connected, switched the outputs on and read a hardware scope frame. **The AD2's USB link is unstable** (it disconnects and re-enumerates repeatedly, over-current counters 0, started before the runtime was installed), so the W2 stream failed within seconds; **the hardware path has run only briefly and is not verified.** To undo the install: `sudo dpkg -r digilent.adept.runtime && sudo rm -r /usr/local/lib/libdwf.so* /usr/local/share/digilent`.
- **pd-simulator on Linux.** `ad2.py` finds `/usr/lib/libdwf.so` (or the loader's); a missing library is the existing device-problem banner, not an import-time crash, so the server and the Preview scope run. README updated (Linux install, troubleshooting rows). Checked without hardware: the server and its API, and the generator against its own ground truth.
- **The Cantol program was run on the board** (STEMlab 125-14 4-Input v1.3, OS 3.00-57, inputs open) and five assumptions in `scpi.py` were wrong: binary blocks are **big-endian**; the trigger sample is at index **8192 − DLY** (the program sent DLY 8192 and so put every trigger on sample 0, where the detector discards pulses); the trigger **hysteresis defaults to 5 mV**, above the program's level; a falling-edge level must be **negative**; and every SCPI round trip cost **50 ms** (delayed ACK) until `TCP_QUICKACK`, which takes a capture from about 300 ms to **29 ms (about 35 a second)**. Measured on the open inputs: 4.4 counts (0.54 mV) of noise on every channel, the six trigger names accepted and firing, trigger at index 8192 in 30 of 30 captures on three sensors and both edges. Numpy 2.4.1 and Python 3.12 are already on the board. A fake SCPI server in the tests now holds the board's wire format (5 tests; two of them fail on the old code, by construction).
- **`--source pdsim`** (`cantol_device/pdsim.py`): replays pd-simulator's own waveforms (W1 on channel 1, W2 on channel 2, scaled copies on the other sensors) through the real detector, phase code, protocol and app; pd-simulator's settings come from a JSON file that is read again when it changes. 6 tests against pd-simulator's own settings (reference locks, a calibration pulse reads at 0° and at its height, PD pulses fall in their two windows with the right sign, changed settings are seen, a refused file keeps the old ones, W2 off triggers nothing); an inverted W1 makes two of them fail.
- **Web version of the field app** (`scripts/serve-field-web.mjs`): the real field bundle, the real Capacitor bridge and WASM in a browser, linked over real TCP to a named Cantol, with the Android side stood in for by `scripts/lib/phone-standin.mjs` (extracted from `verify-field-web.mjs`, which still passes its 91 assertions). `scripts/demo-pdsim-web.mjs` drives it through sign-in, the label, Live and a seven-stop free walk against the board: **it passed twice (20 assertions each)**. The app linked to the real board, locked on pd-simulator's W1, drew the two PD clusters in their windows, and marked a walk of 10, 30, 100, 300, 100, 30, 10 mV settings at 21.2, 29.9, 40.0, 51.1, 39.8, 32.0, 21.3 dBmV (settings 20.0 to 49.5), M4 the strongest. A mark is noisy by about ±3 dB against this source, and the Rate read about 14 a second against about 200 pulses fired (a lower bound, ADR-012 "Result"). pd-simulator refuses a PD peak under 10 mV; the replay logs that and keeps the old settings. Local-only by default, Host/Origin checked, one allowed Cantol.
- **Board access saved.** `mobile/config/redpitaya.local.json` (git-ignored) and `mobile/scripts/rp.sh {ssh|push|pull|info}`; `check-no-secrets.sh` also fails if the file is tracked.
- **Tests:** the lock helper in the detection tests no longer lets the reference lock lapse (a slow CPU outlasts its 12 s; the real engine renews it every 4 s), and the engine's "measuring" floor is a count any CPU reaches; two assertions are now robust to two pulses overlapping (a 90th percentile, not a maximum). The device suite is 33 tests and passes on the board itself in about 90 s.
- **Wiring finding:** pd-simulator's defaults (W1 2 V, pulses to 1.2 V) clip an LV (±1 V) Red Pitaya input; use HV jumpers and `--adc-range hv`, or keep W1 at 0.9 V or less and pulses in the tens of mV on LV.
- **The Red Pitaya rebooted once, unexplained, during the first survey commands** (uptime went from 2:43 to 0 minutes; no persistent journal, so no cause); it did not recur in about an hour of use. Nothing was left running afterwards: the program and the SCPI service on the board are stopped (the SCPI service is inactive again, as found), and `/cantol` keeps the program, its tests, pd-simulator's `signals.py` and the settings file `pdsim.json`.

### Added — device + mobile: the Cantol measurement software for the four-input Red Pitaya, sensors on the Live screen, and Tracking as a free walk (TASK-006 partly, 2026-11-06)
- Requested by the user: "create cantol device to enable live measurement for both measuring partial discharge activity along cable and phase pattern partial discharge like the first mock UI design". Their answers: channel 1 is a sine reference, channels 2 to 4 are the partial discharge sensors; cable mode is a free walk without a line; build first, test on the board later. ADR-011 (Proposed). **The request answers the TASK-006 decision gate: the Cantol detects pulses.** ADR-005 (the protocol) is still unwritten.
- **New `mobile/device/cantol_device`** (Python 3 and numpy, guide `mobile/docs/operations/cantol-device.md`): `python3 -m cantol_device run|selftest --source redpitaya|simulated`. It takes turns arming the scope on each sensor and edge, reads all four channels of each capture, finds pulses (median baseline, a noise deviation from the median absolute deviation, 6 deviations and at least 3 samples, merging within 1.5 µs, edge pulses skipped), follows the mains reference on channel 1 (frequency, offset, lock) and gives each pulse its phase from the reference samples of its own capture (no clock), calibrates to the protocol's counts (`--adc-range`, `--sensor-gain-db`), and streams to the app over the existing link. `--ref-invert` and `--phase-offset` correct the reference; `--no-ref` simulates a missing one. Without a lock the phase is 0 and the status clears the mains-lock bit, so the app hides the phase plot and keeps the tiles.
- **Protocol, backward compatible.** `PdEvent.channel` takes the former reserved byte (the sensor, 0 to 7); `Status` takes an optional trailer (a count, then each sensor's noise floor and rate: `encode_with_sensors`, `sensors_of`). The WASM reports `ch` and `sensors`. Golden vectors and the self-test digest `f7f47846` unchanged; WASM 62,655 bytes. `cantol-mock --sensors N` pretends to have N sensors.
- **App.** The Live screen shows a Sensor selector (All, 1, 2, 3) when the device reports more than one sensor; the plot, Peak, Rate and Noise follow it. In the field build Tracking mode is offered as a **free walk** (`core/freeWalk.ts`, `FreeWalkScreen`, `MarkChart`): mark stations M1 to M12 along a cable, the level at each, rising or falling from the last, the strongest, the distance between two stops when both had a GPS fix, and a warning level; the rules are the span walk's, from the WASM; nothing is saved. `AppConfig.surveysNote` now withholds only Record, Tag and Surveys. The stream hook and the test-data and start-failure notices are shared by Live and the walk (`useStream`, `StreamNotices`).
- Verification: Rust 92 tests (was 86; `cantol-mock/tests/device_program.rs` starts the real program and talks to it with the app's own decoder and calibration); device unit tests 22 against the simulator's ground truth (isolated pulses found with a 2 percent mean amplitude error, phase 0.03° typical and under 0.4° worst over 1,195 pulses, no false pulses in 14 million samples of noise, no lock on a missing, weak, noisy or square reference); Vitest 275 (was 263); the browser walk 91 assertions (was 77), now including the sensor selector and a free walk with marks and a warning; Java and the demo unchanged. Breaking the phase convention, the sensor byte, the engine's release or the detector threshold each makes a test fail (checked).
- **Not run on a board.** The ADC side (`scpi.py`) is written from the SCPI command reference: trigger source names, the trigger delay, the block layout and the speed are unverified. The pulse rate is a lower bound (the scope sees nothing while it is re-armed). Levels are dBmV at the input plus the gain given, not at a sensor's output. `numpy` must be on the board.

### Added — mobile + device: live PD on the field build, streamed from a Cantol that sends test data (TASK-006 partly, 2026-11-04)
- Requested by the user: "i want live measurement but test streaming with synthetic data". ADR-010 (Proposed). **It does not settle the TASK-006 gate** (where pulse detection runs) or ADR-005; it assumes the Cantol detects and sends `PdEvent` batches, as the protocol and the Live screen already did. Nothing in it is measured.
- **Phone to device and back.** The app sends an empty `Start` frame when the Live screen opens and `Stop` when the operator leaves it (`encode_start`, `encode_stop`); the Java `CantolConnection` hands every whole frame it reads to a listener as the bytes it was and gains `send(bytes)` under one write lock shared with the heartbeat; the `CantolLink` plugin emits a `frame` event (only while the app listens) and has a `send` method (`not_connected` when the link is down). `fieldLink.ts` listens first, sends Start, decodes each frame and hands statuses and pulses to the Live screen, and asks for the stream again after the plugin reconnects (the device streams per connection).
- **Rust reads the frames.** `decode_stream_frame` (`cantol-wasm/src/stream.rs`) returns a status in engineering units, a pulse batch with each amplitude in dBmV, `device_error` or `other`, and `no_frame` for a damaged one. The calibration is one placeholder constant in `cantol-dsp` (`dBmV = 20·log10(|counts| × 0.1 mV)`); **0.1 mV per count is not measured** (chosen to land where the demo's numbers do). Golden vectors and the self-test digest `f7f47846` are unchanged; the WASM module is 61,740 bytes (budget 250,000).
- **Test data says so.** `Status.flags` bit 1, `STATUS_SYNTHETIC`: "the numbers this device sends are generated, not measured". The Live screen shows "Test data. The Cantol says these numbers are generated, not measured." while the latest status carries it; Diagnostics says so too. `cantol-mock` and the script set it; the demo build does not (its own badge says what its data is).
- **The Live screen in the field build.** "Start measurement" is enabled when the hotspot, the Cantol and location are up and opens Live PD; the Ready screen says "Ready to measure" again (the "Setup complete" wording from earlier today is gone). `AppConfig.measurementNote` is replaced by `surveysNote`: Record, Tag, Tracking and Surveys stay withheld (no survey server; and test data must not become a saved survey), the tab bar has Device and Live, a note replaces the Record button. New on the screen: "The Cantol did not start sending" with "Try again" when Start cannot be sent, "Waiting for data from the Cantol" after 5 s of silence on an up link, and the stream starting by itself once a link that was down comes back.
- **Fixed on the way:** the Ready screen's "Start measurement" waited for the stream to start before navigating, so a failed start left the button doing nothing and an unhandled rejection; it now goes to Live, which owns the stream and shows the failure (found by the browser walk).
- **`mobile/device/cantol-pingpong.sh` v0.2.0** streams made-up pulses after Start: a level (`--level`, default 38 dBmV) drifting ±4 dB per minute, noise near 6 dBmV, `40 + 10 × (level − noise)` pulses a second in a batch every 50 ms, phase in two lobes around 90° and 270°, 3 percent strays, a status every second with the mains lock and the synthetic bit; `--seed`, `--no-stream`, `--no-mains-lock`. One thread per connection, frames never interleave, a phone that stops reading is dropped after 5 s. Guide: `mobile/docs/operations/cantol-pingpong.md`.
- Verification: Rust 86 tests (was 72; `device_script.rs` reads the script's pulses back through the app's own calibration and decoder: rate, level, lobes, polarity, flags, whole frames in sequence, nothing after Stop, a second Start, `--level`, `--no-stream`, `--no-mains-lock`); Vitest 263 (was 246; including the codec against the real `cantol-mock` streaming and stopping); Java 43 (was 37; five new `CantolConnection` tests, and Start/Stop against the real mock with frames built by the real WASM codec); `scripts/verify-field-web.mjs` 77 assertions (was 60) now walks the Live screen against the real mock (Start, banner, plot, tiles in dBmV, Stop on leaving, a failed Start with retry, a silent device, a lost and restored link asking again); `verify:demo` 168 screens and 350 assertions unchanged.
- **Not run on a phone or on the Red Pitaya.** Unknown: the Capacitor bridge at one `frame` event every 50 ms (screen on and off), the Red Pitaya keeping the 50 ms schedule, the script's stream on the real device. To try it, the Red Pitaya needs the new script (it is on `/cantol` as v0.1.0, which ignores Start) and the phone needs the new APK.

### Fixed — mobile: the location status flickered between "On" and "No fix", and the Ready screen said "Ready to measure" over a disabled button (TASK-005, 2026-11-04)
- Reported from a phone with the Red Pitaya connected: the Location row alternated between "On" and "No fix" with location on, and "Start measurement" stayed disabled.
- **Location.** `@capacitor/geolocation`'s `watchPosition` takes its interval from the `timeout` option (10 s here) and caps the rate at a `minimumUpdateInterval` of 5 s, so a fix arrived about every 10 s while the app calls 5 s without one "no fix". The watch now sets `interval` and `minimumUpdateInterval` to 1 s (`GPS_WATCH_INTERVAL_MS`); `NO_FIX_AFTER_MS` moved to `core/wizard.ts` and a test keeps the two apart. The earlier test had pinned the faulty options. The browser walk's stand-in used to deliver a fix every 0.6 s whatever was asked, which hid the bug; it now delivers at the rate the plugin would for the options given (read from its source) and watches the Location row for 12 s. With the old rate it fails ("No fix" in 29 of 48 checks); with the fix, 3 of 3 runs pass (60 assertions).
- **The disabled button is by design** (TASK-006 is gated, ADR-008 decision 7), but the screen did not say so: it announced "Ready to measure" with a small grey note. A build that cannot measure now shows "Setup complete." and a card "Measurement is not in this version." with the reason. The demo build is unchanged. *(Superseded the same day by the entry above: the field build can now show Live PD, and "Ready to measure" is back.)*
- Vitest 246 (was 245).

### Added — mobile + device: the Cantol label values typed on the phone, a MAC check of the connected device, and a Cantol-side ping-pong script (TASK-005, 2026-11-04)
- ADR-009 (Proposed). A new first-run screen, `/setup/device` ("Enter the Cantol label"), asks for the hotspot name (at most 32 bytes), the password (8 to 63 plain characters, hidden, Show toggle) and the Cantol's MAC address (twelve hex digits in any notation, shown as `00:26:32:F0:1A:BC`). It is wizard step `DEVICE_SETUP`, before the hotspot, until the values are saved; the hotspot screen shows them and links back to edit them. - The device proves which unit it is: the PONG and the beacon get an optional trailing six-byte MAC field (`Pong::encode_with_mac`, `Beacon::encode_with_mac`; the 26- and 18-byte base layouts, the golden vectors and the self-test digest `f7f47846` are unchanged; all zeros means "not reported"). `decode_pong` and `decode_beacon` report `"mac"`. `cantol-mock` reports `02:CA:57:00:00:01` (option `--mac`).

The Cantol screen says "A device answered at ... with MAC address ..., not the ... you entered" with a "Check the label values" button; saving a different MAC address drops the link and searches again, saving only a name or password keeps it. POSIX `sh` plus a `python3` responder it writes out; it changes no network configuration.

### Fixed — mobile: the field build stuck on the welcome screen when location was off (TASK-005, 2026-10-26)
- Reported from a phone: after signing in, the welcome screen's Continue did nothing. Cause: Continue waits for the wizard's first checks to answer, and `@capacitor/geolocation` rejects `checkPermissions()` and `requestPermissions()` with "Location services are not enabled" (`OS-PLUG-GLOC-0007`) whenever location is switched off, the usual state of a phone. The wizard asked for permission and services together, swallowed the failure and retried silently forever. The browser walk of 2026-10-25 missed it because its stand-in always answered.
- Fixed at the cause: with location off, the permission is read through a new native `GnssHelper.permissionState` (a plain `checkSelfPermission`), and asking for it sends the operator to the location settings, once per tap. Fixed in general: a new wizard event `CHECKS_GAVE_UP` opens the first screen after 4 s with unanswered checks counted as "not met", so no failed or hung check can trap the app on that screen; the polls go on and correct it. Visible: the welcome screen says "Still checking this phone" and which check failed and why, the GPS screen shows a location failure, and `enableGps` no longer swallows errors.
- `scripts/verify-field-web.mjs` now models the real plugin: the phone starts with location off, the plugin rejects both permission calls while it is off, and a plugin fails at the start. 31 assertions, 3 of 3 runs; with both fixes undone it fails on this bug. Vitest 203 (was 194); `verify:demo` and the Java tests unchanged.
- Still not run on a phone after the fix.

### Fixed
- `transformer_readings` PostgREST embed was read as an array but is actually returned as a single object (it has a `UNIQUE` FK to `surveys`, unlike `pd_readings` which is genuinely one-to-many) — every transformer showed "no data yet" until fixed in `lib/data/assets.ts` and `app/api/assets/[id]/route.ts`
- Map click hit-testing: a `Polyline` rendered after a transformer marker could intercept clicks meant for that marker when the two visually overlapped; lines now render before markers in `MapView.tsx`
- Dev server was unreachable when opened via a forwarded/LAN URL instead of `localhost` — Next.js blocks cross-origin requests to dev-only JS resources by default, so every client component (including the map) silently failed to mount; fixed with `allowedDevOrigins` in `next.config.ts`. That fix later went stale on its own (hardcoded LAN IP from a since-changed network re-triggered the exact same "stuck forever on 'Loading map…', zero console errors" symptom) — `allowedDevOrigins` now computes the machine's current LAN IPs at server startup via `os.networkInterfaces()` instead of hardcoding one
- PD readings were modeled as linking to `poles` — wrong: a pole is a support structure with no reading, the actual measurement location sits *between* poles. Split into a separate `measurement_points` entity (`pd_readings.pole_id` → `measurement_point_id`, migration `003_measurement_points.sql`)
- "Add Asset" button appeared completely unresponsive (no visible modal, no console error) — the modal overlay (`MapApp.tsx`) had no explicit `z-index`, and Leaflet's own controls (`.leaflet-top`/`.leaflet-bottom`, z-index 1000) escape into the shared stacking context because the map container establishes none of its own, silently painting over the modal even though it was correctly mounted and interactive in the DOM. Fixed with `z-[1100]` on the overlay
- Upstream Leaflet 1.9.4 bug (`Cannot read properties of undefined (reading '_leaflet_pos')`, missing a null-check in `getPosition()` that was fixed upstream but never released to npm) — patched via `patch-package`
- Stray `body { font-family: Arial }` rule left over from the `create-next-app` scaffold was silently overriding the intended font the whole time (unlayered CSS beats Tailwind's layered utilities) — removed
- A negative `z-index` on a decorative hero SVG escaped its intended stacking context and painted entirely behind the page's opaque background, making it invisible — fixed with `isolate` on the containing section
