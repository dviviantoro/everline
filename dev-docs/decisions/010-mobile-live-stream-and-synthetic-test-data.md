# ADR 010 — Mobile field build: live PD over the held link, fed by a Cantol that sends synthetic test data

> Template: `ai-rules/decisions/001-architecture.md`. Related: ADR-003, ADR-005 (still to be written), ADR-008, ADR-009. Amends ADR-008 decision 7 (the field build "cannot measure") and decision 3 (what native code does on the held link); nothing else in them changes.

## Status

Proposed — 2026-11-04. The user asked for it in the field-build session: "i want live measurement but test streaming with synthetic data". The design choices below were made while building it and are for the user to accept or change. **Not run on a phone or on the Red Pitaya.** It does not lift the gate on TASK-006: where pulse detection runs (Cantol or phone) is still undecided, and nothing here measures anything.

---

## Context

- ADR-008 decision 7 left the field build unable to measure: "Start measurement" was disabled, the Live screen unreachable. The user wants the Live screen working end to end now, with the Red Pitaya streaming **made-up** data, so the pipeline (device, TCP, Java, bridge, Rust, screen) can be tried on real hardware before the real measurement software exists.
- The placeholder protocol (`cantol-proto`) already defines the messages: `Start`/`Stop` from the phone, `Status` about once a second and `PdEvent` batches from the device. `cantol-mock` already streams them. What was missing was the phone's side: the Java link read every frame after the first and dropped it, the app had no way to send a frame on the held link, and nothing decoded a status or a pulse batch.
- The decision gate (TASK-006) is open. This ADR must not settle it by accident. Streaming pulse events assumes the **Cantol detects pulses**, which is what the protocol and the Live screen's `PdEventSample` already assume; if the answer is "the phone detects", the pulse frames become waveform frames and the Rust decode changes, but the transport, the Start/Stop handling, the test-data flag and the screen do not.
- Data that is made up must never be taken for a reading. A field app that shows plausible dBmV values on a plot is exactly where that mistake would be made.
- The survey API (line assets, measurement points, upload) is absent from the field build, so Record, Tag, Tracking and Surveys cannot work in it.

---

## Decision

1. **Start and Stop.** The phone sends an empty `Start` frame to ask for pulses and an empty `Stop` to end them (`handshake::start_frame`, `stop_frame`, exported as `encode_start`, `encode_stop`). The device streams per connection. The wizard already starts the stream when the Live (or Tracking) screen opens and stops it when the operator leaves, so those are the only two moments frames are sent. If the plugin reconnects on its own, the field link sends `Start` again, because the new connection streams nothing until asked; it does so only if a stream was wanted.
2. **Native code still moves bytes.** `CantolConnection` hands every whole frame it reads (answers to the heartbeat included) to a listener as the bytes it was, and gains `send(bytes)`, which shares the socket with the heartbeat under one write lock so their bytes never mix. The `CantolLink` plugin emits a `frame` event per frame (base64) **only while the app listens for `frame`**, and has a `send` method; it rejects with `not_connected` when the link is down. Java never reads a CRC or a message.
3. **Rust turns frames into numbers.** `decode_stream_frame` (in `cantol-wasm`, built on `cantol-proto` and `cantol-dsp`) returns one line of JSON per frame: a status in engineering units (°C, percent, the noise floor in dBmV, rate, queue, mains lock, synthetic), or a pulse batch with each amplitude in dBmV, or `device_error`, or `other`. A damaged or incomplete frame is `{"error":"no_frame"}` and the app counts it and goes on.
4. **Calibration is one placeholder constant.** `cantol-dsp::calibration`: `dBmV = 20·log10(|counts| · 0.1 mV)`, with zero counts treated as one. 0.1 mV per count is **not measured**; it is chosen so levels land where the demo's do (noise floor a few dBmV, a strong discharge at 40 and above). Every level the app shows from a real device is provisional until the Red Pitaya's ADC range and front end are characterised. The conversion lives in Rust and nowhere else (the script repeats the constant to make pulses of a chosen level, and its test reads them back through the Rust function so the two cannot drift).
5. **Test data says so, on every status.** `Status.flags` gets a second bit, `STATUS_SYNTHETIC` (`0b10`): "the numbers this device sends are generated, not measured". A device that sets it sets it in every status. The Live screen shows a banner, "Test data. The Cantol says these numbers are generated, not measured.", whenever the latest status carries the bit; the Diagnostics screen says "test data, generated by the device". The mock and the script set it. The demo build does not (its own badge says what its data is), so its screens do not change.
6. **The field build offers Live and nothing that records.** *(Amended 2026-11-06 by ADR-011: Tracking is offered too, as a free walk with no line; Record, Tag and Surveys are still withheld.)* `AppConfig.measurementNote` is replaced by `surveysNote`: when set, Record, Tag, Tracking and Surveys are not offered, their routes lead back to the Ready screen, the tab bar has Device and Live only, and the Live screen shows the note in place of the Record button. "Start measurement" is enabled when the hotspot, the Cantol and location are all up, and the Ready screen says "Ready to measure" again. Recording is withheld on purpose, not only because the line assets cannot be loaded: test data must not become a saved survey.
7. **The synthetic source is the device, not the app.** `mobile/device/cantol-pingpong.sh` (version 0.2.0) streams made-up pulses to a phone that has sent `Start`, one connection at a time on its own thread. The signal has the shape the demo simulates: a level (`--level`, default 38 dBmV) drifting by ±4 dB over 60 s, a noise floor near 6 dBmV, a rate of `40 + 10·(level − noise)` pulses a second (at most 600) in a batch every 50 ms, phase in two lobes around 90° and 270° (polarity and the sign of the counts follow the lobe) with 3 percent strays at the noise floor, widths of 40 to 600 ns, a status every second with the mains lock set (`--no-mains-lock` clears it to try the "Ref not locked" screen) and always the synthetic bit. `--seed` makes a run repeatable, `--no-stream` ignores `Start` (the earlier ping-pong-only behaviour). `cantol-mock` sets the same bit.

Alternatives considered:

| Alternative | Outcome |
|---|---|
| Generate the test pulses inside the app (a simulated link in the field build) | Rejected: the point is to exercise the real chain, device to screen, on the Red Pitaya. The demo build already shows simulated pulses. |
| Decode frames in Java and send finished objects to JavaScript | Rejected: protocol meaning would live in two languages (ADR-008 decision 3). |
| Send every frame to JavaScript all the time | Rejected: the plugin checks for listeners and does nothing until a screen needs the stream; the status answered to the heartbeat every 2 s would otherwise cross the bridge for no reader. |
| Let the operator Record test data and save it | Rejected: it would put generated numbers into the survey store and, once upload exists, onto the server. |
| Hide the synthetic flag from the screens and rely on the operator knowing | Rejected: the screen cannot tell a Red Pitaya running the script from one running real software, only the device can, and a banner costs one line. |
| Wait for ADR-005 and the decision gate | Not what was asked; the choices here are marked placeholders and cost a protocol bit and one constant to change. |

## Consequences

### Positive

- The whole chain can be tried on the real Red Pitaya and a real phone: Start, a stream of pulses and statuses, the plot and tiles, Stop on leaving, a lost link recovering and asking again.
- The Rust codec, not the screens, owns units and calibration; the screens already took dBmV.
- Nothing about the existing protocol bytes changes: the golden vectors and the self-test digest `f7f47846` are untouched (the status flag uses a bit the layout already had, and `Start`/`Stop` existed).

### Trade-offs

- The assumption that the Cantol detects pulses is now built into a second place (the Rust decode of `PdEvent`). If the gate decides otherwise, that decode and the script's generator change.
- Frames cross the Capacitor bridge as base64 events, about twenty a second while streaming (a batch every 50 ms). Fine at this rate; a device that sent several hundred small frames a second would need batching in the plugin.
- The 0.1 mV per count calibration makes every number shown from a real device provisional. The "Test data" banner covers the script; real software that sets no synthetic bit would show unverified levels as if they were readings. Replacing the constant is the first thing to do when the front end is characterised.
- The Live screen has no survey to attach a reading to in this build, so the only thing a field test can show is that the numbers move and that the link holds.

### Risks (none of these has run on a phone or on the Red Pitaya)

- The Capacitor bridge delivering a `frame` event twenty times a second to a WebView in the background or with the screen off; `hasListeners` and `notifyListeners` from the link's thread behave as the code expects in tests with a fake, not in Capacitor.
- A phone whose hotspot or Wi-Fi power saving delays frames enough that the 2 s heartbeat window (one silent interval) reports the link lost while pulses are arriving.
- Python's 50 ms scheduling on the Red Pitaya under load: pulses are generated from elapsed time, so a late tick sends a larger batch (capped at half a second's worth), never fewer pulses.
